# Internationalization

## Locales

Five supported locales: `en` (default), `ja`, `fr`, `zh-CN` (Simplified Chinese), `zh-TW` (Traditional Chinese, Taiwan usage)

The Chinese locales keep their canonical codes internally (Sanity `language` values, hreflang, `lang`) but are served under lowercase URL prefixes: `/zh-cn` and `/zh-tw` (see `localePrefix.prefixes` in `i18n/routing.ts`).

## Translation Files

Location: `messages/{en,ja,fr,zh-CN,zh-TW}.json`

### Naming Convention

- **Namespaces**: PascalCase (e.g., `"ContactForm"`)
- **Keys**: snake_case (e.g., `"submit_button"`)

```json
{
  "ContactForm": {
    "submit_button": "Send message",
    "success_message": "Thank you for contacting us"
  }
}
```

## Usage

### Server Components

Use `getTranslations` for copy. Use `getLocale` when a server component needs the active locale (e.g. Sanity query params, metadata).

```tsx
import { getTranslations } from 'next-intl/server'

export default async function Page() {
  const t = await getTranslations('ContactForm')

  return <button>{t('submit_button')}</button>
}
```

Locale resolution is centralized in `i18n/request.ts`. Do not read `locale` from route `params` in pages or layouts — `getLocale()` returns the middleware-resolved locale. For routes with additional params, fetch them from `params` and locale from `getLocale()` in parallel:

```tsx
const [{ house }, locale] = await Promise.all([params, getLocale()])
```

Invalid locales are rejected in `i18n/request.ts` via `notFound()`.

### Client Components

```tsx
'use client'
import { useTranslations } from 'next-intl'

export function ContactForm() {
  const t = useTranslations('ContactForm')
  return <button>{t('submit_button')}</button>
}
```

## Key Rules

- All user-facing strings must be in `messages/en.json`
- Never hardcode text in components
- Use ICU message format for plurals and arguments
- Keep all locale files synchronized with `en.json`
